Implementation plan

Replace LLM scores with evaluation checks

Make the agent collect browser evidence for explicit checks while Caracara—not the model—computes the final pass rate.

Draft Revision 1

Context

Why this work matters

Today each scenario gives an LLM a scoring prompt and accepts a model-generated number from 0 to 1. That produces compressed, flattering scores around 0.8–0.9 and makes regressions hard to interpret.

The replacement is a clean break: each scenario owns an ordered list of concrete evaluation checks. The agent uses the existing Chrome DevTools browser control to perform the flow and returns one verdict plus browser evidence for every check. Caracara validates completeness and calculates passed checks / total checks as the final percentage. The model never emits a number.

This plan intentionally excludes Playwright, compatibility adapters, score migration, weights, fuzzy rubrics, and a separate improvements backlog. Per-check evidence supplies the first useful defect record; exploratory findings can be designed later.

Across the cutover

Global requirements

Scoring

No model-generated score

The runner output contains only an execution summary and check verdicts. A completed run’s pass rate is derived as round(100 × passedCheckCount / totalCheckCount). failed and not_observed both remain in the denominator; an infrastructure-failed or interrupted run has no final pass rate.

Contract

Three explicit verdicts

passed means browser evidence confirms the expectation; failed means observed behavior contradicts it; not_observed means the agent could not reach or inspect it. Every verdict requires concise concrete evidence. Missing, duplicate, or unknown check IDs invalidate the entire scenario result as runner_failed.

Browser

Chrome control only

Keep the current run-scoped Chromium process, CDP endpoint, and chrome-devtools-mcp integration. Both Codex and Claude adapters receive that same Chrome MCP configuration. Do not add Playwright, browser assertions, screenshots-as-scores, or a second browser lifecycle.

Cutover

Destructive, versioned replacement

Delete existing scenario dependencies, scenarios, scenario results, and runs; preserve projects and phases. Remove all old fields and compatibility code, bump the HTTP namespace/API version to v2, and publish CLI 0.2.0 so old clients fail clearly instead of submitting legacy payloads.

Phase 01

Ship the check-based evaluation loop

One atomic vertical slice replaces authoring, contracts, execution, persistence, aggregation, and result presentation together.

Target Convex schema

Embed checks because they have no lifecycle outside their scenario. Snapshot the authored checks on each result, then store a separate verdict array keyed to that snapshot. Array position is the authoring order; the stable string ID survives reordering.

const evaluationCheck = v.object({

End-to-end implementation

  • Authoring: replace the scoring-prompt textarea with an ordered check editor using shared shadcn primitives. A check has name and expectation; add, edit, delete, and move controls preserve stable IDs. Drafts may have zero checks, but activating a scenario requires 1–20 checks, unique IDs, non-empty names (≤120 chars), and expectations (≤2,000 chars).
  • Contracts and API: update domain and HTTP Zod schemas, generated Convex-facing mappers, route tests, and API documentation. Start-execution stores the exact check snapshot. Submit-result accepts only result status, check results, summary/failure details, and timestamps; the server rejects any check set that does not exactly match the snapshot.
  • Runner prompt: list checks by stable ID and expectation. Tell the agent to use Chrome tools, perform the scenario once, evaluate only what it can support with browser evidence, and never calculate a score. Build a per-scenario JSON Schema for executionSummary plus checkResults[]; follow parsing with exact set and non-empty evidence validation.
  • Browser session: move shared Chromium/CDP startup to runner-session infrastructure. Retain Codex’s current chrome-devtools-mcp arguments; generate an equivalent temporary MCP JSON file for Claude’s verified --mcp-config and --strict-mcp-config flags. One run reuses one Chrome profile/session and closes it in the existing finally path.
  • Execution semantics: a completed scenario may contain failed checks without failing the run or stopping dependencies. Only malformed output, runner/browser failure, dependency failure, or interruption changes infrastructure status. The CLI prints 7/9 checks passed, not a decimal score.
  • Aggregation: finalize the run server-side by reading completed scenario results and atomically writing passed/total counts. The API exposes a nullable derived passRate integer (0–100) only when run status is completed; persisted source-of-truth remains the two counts.
  • Results UI: replace score cards and improvement blocks with check totals and an ordered result list. Use neutral/success/destructive tokens for passed/failed/not-observed, show evidence inline, and keep execution failures visually separate from product-check failures.
  • Specs: revise product scope, domain model, scenario authoring, execution/scoring, API contracts, storage, frontend, and CLI specs so “score” means only the derived final pass rate and every legacy scoring-prompt example is removed.

Destructive deployment sequence

  1. Deploy a temporary internal mutation against the old schema that deletes, in dependency order, scenarioResults, runs, scenarioDependencies, and scenarios. Invoke it in development and production; verify all four counts are zero. Preserve projects and phases.
  2. Deploy the final schema/API/UI and remove the temporary mutation in the same cutover branch. Because no legacy documents remain, all new fields can be required immediately; do not add optional dual-read/dual-write paths.
  3. Publish CLI 0.2.0 after the web API v2 deployment. Verify CLI 0.1.x receives a version mismatch and cannot create runs.

Verification

  • Unit tests cover check validation, stable reorder IDs, runner prompt/schema generation, exact returned-ID matching, verdict counting, nullable pass-rate rules, and Codex/Claude Chrome MCP arguments.
  • Convex tests cover ownership, snapshot immutability, rejected missing/duplicate/unknown check results, completed scenarios with failed checks, run finalization counts, and cascade deletion.
  • API route and CLI integration tests replace all score fixtures and prove that malformed LLM output becomes runner_failed without partial check persistence.
  • Manual acceptance: author three checks, run against a deliberately broken local UI through Chrome control, confirm one pass/one fail/one not-observed with concrete evidence, see 33%, and confirm no Playwright package/process/config or model-generated numeric score exists.
  • Run pnpm lint, pnpm typecheck, package/web tests, and pnpm build.

Acceptance requirements

Integrity

Every authored check is accounted for

A completed result has exactly one verdict for every snapshotted check, no extras, and non-empty evidence. Validation occurs in both CLI and Convex so a modified client cannot bypass it.

Regression signal

The final percentage is reproducible

The same stored verdicts always produce the same counts and percentage. No rationale, confidence, model preference, or hidden weighting changes the number.
