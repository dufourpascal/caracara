Implementation plan

Failed-check screenshot evidence

Make every failed check in a Codex run reviewable with a stored screenshot, then remove that evidence when its run is deleted.

Complete Revision 2 Two vertical phases Target CLI 0.3.0 and API v3

Context

Current behavior and chosen boundary

Caracara already gives Codex a run-scoped Chrome DevTools MCP server and receives one structured verdict plus text evidence per check. Chrome DevTools MCP can save a screenshot to a caller-selected file, and the Codex SDK can continue the same thread for a corrective turn. The CLI currently ignores tool artifacts, the hosted data model has no file records, and run deletion removes only scenario-result documents.

This plan interprets "a check fails" as the failed verdict. A not_observed result documents missing evidence and does not require a screenshot. The first release captures screenshots for Codex runs only. Storage and UI contracts stay runner-neutral so Claude can adopt the same flow later.

Recommended capture contract Add deterministic screenshot file paths to the main runner prompt. Do not add local paths or image data to the model's JSON response. After Codex returns verdicts, the CLI checks the expected files, uploads only screenshots for failed checks, and submits the normal result after every required upload is durable.

References: Codex SDK, Chrome DevTools screenshot tool, and Convex File Storage.

Across all phases

Global requirements

Invariant

One image for each failed Codex check

A completed run using the new evidence policy cannot persist a failed check without exactly one ready screenshot attached to the same run, scenario result, and check ID. Passed and not-observed checks do not require images.

Security

Treat screenshots as private run data

Never put image bytes, credentials, or local paths in result JSON, logs, or URLs. Authenticate uploads and reads, verify project and run ownership, and serve images through a same-origin route that checks access on every request. Do not expose reusable Convex storage URLs to the browser.

Constraint

Bound file type and size

Capture the visible viewport as WebP at quality 80, not a full-page image. Accept only image/webp up to 3 MiB. Verify the file signature, content length, and SHA-256 digest before attaching it. This keeps uploads and authenticated image responses below current platform limits.

Compatibility

Snapshot the evidence policy on each run

Add evidencePolicy to runs with text_only for historical and v2 runs and failed_check_screenshot for API v3 runs. Enforce screenshots only for the new policy. Ship backend v3 support before publishing CLI 0.3.0, and retain v2 for one release window if existing 0.2 clients still run.

Reliability

Make retries safe

Use the run ID, scenario result ID, check ID, and SHA-256 digest as the upload identity. A repeated upload of the same bytes returns the existing artifact. A replacement swaps the storage reference and deletes the old blob. Lost responses must not create duplicate evidence.

Phase 01

Capture, upload, and review

Deliver one complete path from a failed Codex verdict to a compact, clickable screenshot in the run detail.

End-to-end sequence

  1. The CLI creates a scenario-specific temporary evidence directory. Every check gets a deterministic path such as <temp>/<check-id>.webp.
  2. buildRunnerPrompt tells Codex to call Chrome DevTools take_screenshot after observing each failure, using the exact path, WebP format, quality 80, and the visible viewport. It must not capture passed or not-observed checks.
  3. After the structured turn returns, the CLI validates each expected failure image. If one is missing, it makes one corrective call on the same SDK thread asking only for the missing screenshots. A second miss turns the scenario into runner_failed because required evidence is incomplete.
  4. The CLI posts each validated image directly to an authenticated Convex HTTP action. The action verifies the Clerk token, run ownership, running scenario result, check ID, type, size, digest, and evidence policy before storing the blob.
  5. The action inserts or idempotently reuses a runEvidence record. If database attachment fails, it deletes the just-created blob before returning an error.
  6. Only after all required uploads succeed does the CLI call the existing result-submission endpoint. The mutation rejects a completed failed check unless its ready evidence record exists.
  7. The run-detail query returns artifact metadata grouped by scenario result and check. The frontend requests image bytes from an authenticated same-origin route and renders a constrained thumbnail below the text evidence.

Stored shape

Add a runEvidence table with projectId, runId, scenarioResultId, checkId, kind, storageId, contentType, byteSize, sha256, and createdAt. Index by run, scenario result, result plus check, and storage ID. The table is the attachment relationship; do not embed mutable storage URLs in check results.

API and serving contracts

  • API v3 run creation returns the authenticated Convex evidence-upload action URL and snapshots failed_check_screenshot on the run.
  • The CLI sends the bearer token plus run, scenario result, check, size, and digest headers with the WebP body. The action returns the stable artifact ID and metadata.
  • submitScenarioResult keeps its textual check-result payload, but the backend adds the ready-evidence invariant for v3 Codex runs.
  • GET /api/run-evidence/[artifactId] uses the Clerk browser session, verifies artifact ownership through Convex, fetches the storage object server-side, and responds with Cache-Control: private, no-store.

Run-detail interaction

For a failed check with evidence, place a button-wrapped image below the current text evidence. Use a fixed compact viewport around 15rem by 9rem, object-contain, lazy loading, a border-first surface, and an explicit "Open screenshot" label. Clicking opens the original image in a Radix/shadcn Dialog sized to the viewport. Escape closes it, focus returns to the thumbnail, and the image has alt text based on the check name. Historical failures without an artifact keep their text evidence and show no empty image frame.

Phase requirements

CLI

Prompt and validate deterministic capture

Keep image paths out of structured output. Prompt exact destinations, validate files after the turn, retry capture once on the same thread, and always remove local evidence files after upload or runner shutdown.

Backend

Upload directly into Convex storage

Use an authenticated Convex HTTP action so image bytes do not pass through the Vercel application route. Store and attach in one action, compensate on attachment failure, and make identical retries return the existing artifact.

Contract

Reject incomplete failed evidence

For runs whose evidence policy requires screenshots, result submission checks that failed IDs match ready screenshot records exactly. A failed upload is retried with bounded backoff; exhaustion reports a runner failure instead of storing a failed verdict without its required image.

Frontend

Compact thumbnail and full-screen review

Show the screenshot only under its failed check. Keep it small and uncropped, load it lazily, and open it in an accessible Dialog using existing neutral shadcn tokens. Include loading, unavailable, and image-load-error states.

Verification

Prove the complete path

Add unit and integration coverage for prompt text, file validation, retry behavior, upload authentication, ownership, digest and type checks, idempotency, submission enforcement, query shaping, and dialog accessibility. Manually run one known failing localhost scenario and inspect both thumbnail and full-screen image.

Phase 02

Deletion and recovery

Close every cleanup path so screenshots cannot outlive their run or accumulate after interrupted uploads.

Lifecycle states

StateOwnerExit and cleanup
Local captureCLI temporary directoryDelete after confirmed upload; recursive cleanup when the runner closes or errors.
Stored and attachedConvex storage plus runEvidenceAvailable only while the owning run and result exist.
ServedAuthenticated Next.js responseNo public URL or durable browser cache; each request rechecks access.
DeletedRun deletion helperDelete storage blobs, evidence rows, scenario results, then the run.

Cascade behavior

Extend deleteRunAndResults rather than adding a second deletion path. Query evidence through by_run, delete every storage object and evidence row, then delete scenario results and the run. Project deletion already calls this helper, so it inherits the same cleanup. Update the confirmation text to state that screenshots are permanently removed.

Incomplete execution cleanup

  • If a scenario ends as runner-failed, dependency-failed, or interrupted, remove any screenshots uploaded while that scenario result was running.
  • If a running scenario result is restarted, clear its attached evidence before resetting the result snapshot.
  • If completed verdicts do not use an uploaded check image, remove that image before finalizing the result.
  • Keep direct-upload action compensation for validation and database failures. Add a daily, paginated orphan audit over Convex _storage that deletes screenshot objects older than 24 hours with no runEvidence.by_storage_id record. Document that future storage features must register their storage IDs before enabling this audit.

Deletion proof

The manual acceptance test captures a failed-check screenshot, records its artifact and storage IDs, deletes the run from the UI, confirms the run query returns null, confirms the evidence row is gone, and confirms the old authenticated image endpoint returns 404. Repeat through project deletion to prove the shared cascade.

Phase requirements

Deletion

Delete images with runs and projects

Make the existing run deletion helper the single owner of screenshot cleanup. A storage deletion failure must fail the mutation without silently dropping the database reference, so the user can retry.

Recovery

Clean incomplete scenario evidence

Delete evidence when execution does not produce a completed result, when a running result restarts, or when the final verdict set no longer references an uploaded image. Keep these rules in shared Convex helpers.

Operations

Reconcile rare orphaned blobs

Paginate storage metadata, ignore files younger than 24 hours, and delete only objects that have no evidence record. Log counts and storage IDs, never image contents. Keep the job disabled until tests prove it cannot target unrelated storage.

Verification

Test every terminal path

Cover run deletion, project deletion, interrupted scenarios, upload compensation, duplicate upload retries, stale authenticated image requests, and orphan-audit safety with real Convex storage behavior where practical.
