Implementation plan

Direct scenario authoring from the CLI

Add eight narrow commands that let an interactive AI agent change phases, scenarios, and checks immediately without giving an evaluation agent the chance to rewrite a running evaluation.

Complete Revision 2

Context

Why this work matters

Caracara already has authenticated Convex mutations for phase and whole-scenario editing, while the published CLI only reads scenarios and submits runs. This change exposes a deliberately small authoring interface through the existing CLI login and project selection.

The commands write the live scenario records directly. There is no proposal object, review screen, scenario-version table, delayed activation, or undo feature. The existing scenarioResults snapshots remain because they are run evidence, not authored scenario versions.

A direct command using the same owner credential is unsafe during evaluation. The minimum enforceable boundary is therefore a backend rule that rejects every phase or scenario mutation while the project has a running run. Outside a run, changes take effect immediately.

Across all phases

Global requirements

CLI scope

Exactly eight mutation commands

Expose addPhase, editPhase, removePhase, createScenario, updateScenario, addCheck, removeCheck, and updateCheck. Do not add a generic patch command or scenario deletion command.

Behavior

Direct, immediate writes

Each successful command updates the current Convex record and returns the changed entity or concise deletion result. There is no confirmation prompt, proposal state, authoring draft workflow, activation delay, or undo path. The existing scenario draft status remains part of the product model.

Integrity

Lock authoring during a run

All Convex phase and scenario writes, including existing web mutations, return a conflict while that project has a running run. This is a write lock, not delayed activation: once the run finishes or is removed, the next command writes immediately.

Access

Reuse existing owner authentication

Commands use the current caracara login bearer token, selected project resolution, API-version header, and Convex ownership checks. Do not introduce roles, authoring tokens, API keys, or a second login flow.

Storage

No authoring version model

Do not add version numbers, version tables, revision history, restore actions, or audit snapshots. Continue overwriting live scenarios and checks in place. Past runs keep their existing copied instructions and checks so their recorded evidence stays intelligible.

Phase 01

Ship direct authoring end to end

One vertical slice adds the command interface, authenticated HTTP operation, atomic Convex writes, run lock, documentation, and verification.

Command contract

Add these top-level Commander commands using the existing --project <slug> override and selected-project fallback. Commands are non-interactive and print one JSON result to stdout so Codex can verify exactly what changed. Errors go to stderr with a non-zero exit code.

Command Required input Behavior
addPhase --name Append a phase at the next order.
editPhase --phase, --name Rename one phase without changing its order.
removePhase --phase Keep current behavior: delete the phase, unassign its scenarios, remove dependencies touching those scenarios, and normalize phase order.
createScenario --name, --instructions Create a draft with an optional slug, phase, and repeated dependency slugs. Checks start empty.
updateScenario --scenario plus at least one change Partially update name, slug, status, instructions, phase assignment, or the complete dependency set. Never alter checks.
addCheck --scenario, --name, --expectation Generate a UUID and append the check.
removeCheck --scenario, --check Remove one check. Reject removal of the last check from an active scenario.
updateCheck --scenario, --check plus name or expectation Update content while preserving the check ID and array position.

--scenario uses the existing scenario slug. --phase accepts an ID, order, or exact name; --check accepts an ID or exact name. The CLI resolves these through existing scenario and execution-plan GET requests and fails on zero or ambiguous matches. This avoids extra discovery commands while retaining stable IDs for writes.

Contracts and HTTP

  • Add one Zod discriminated union for the eight request shapes and one corresponding response union in packages/contracts/src/api.ts. Reuse the existing domain validators and limits.
  • Add one authenticated POST /api/v3/projects/[projectSlug]/authoring route. Its body contains operation and the operation-specific input. Keep namespace v3 and minimum CLI 0.3.0 because the endpoint is additive.
  • Add one submitAuthoringOperation client function in packages/caracara/src/api.ts. Command handlers in commands.ts resolve project and resource references, validate flags, call it, and print the parsed response.
  • Bump the publishable caracara package and its internal contracts package to 0.4.0. Do not create a compatibility adapter or force existing 0.3 clients to upgrade.

Atomic backend behavior

  • Reuse the existing phase create, update, and remove mutations after adding the shared running-run guard.
  • Reuse scenario create with status: draft and an empty check array. Add a focused partial scenario mutation so updateScenario does not fetch and rewrite checks or unchanged fields.
  • Add three focused check mutations. Each reads and validates the owned scenario inside the transaction, edits only evaluationChecks, updates updatedAt, and returns the current scenario. The existing 20-check limit, required active check, UUID, name, and expectation rules remain authoritative.
  • Add runs.by_project_status and one shared assertProjectAuthoringUnlocked helper. Call it inside every phase and scenario write mutation, including existing web-only reorder and delete mutations, so another client cannot bypass the lock.
  • Map a locked project to HTTP 409 with the running run name. Do not queue the change. The caller can retry after the run reaches a terminal state or is removed.

Deliberate omissions

No frontend changes, generic JSON Patch, bulk import, scenario deletion, phase reorder, check reorder, confirmation prompt, change preview, audit log, authoring token, version model, activation scheduler, or undo action. Existing web authoring continues to use its current UI and shares the run lock.

Specs and documentation

Update scenario authoring, execution, API, authentication, storage, and package specs. State that live scenario records are overwritten, completed runs retain their existing snapshots, CLI authoring is owner-only, and authoring is unavailable while a project run is active. Add the eight commands and examples to the CLI README/help text.

Verification

  • Contract tests cover every discriminated request and response, missing fields, invalid slugs and UUIDs, oversized text, and unknown operations.
  • Convex tests cover ownership, phase cleanup semantics, partial scenario updates that preserve checks, check ID/order preservation, maximum and minimum check counts, dependency validation, and all writes blocked by a running project run.
  • Route tests cover authentication, ownership, operation dispatch, validation errors, not-found targets, and the 409 running-run conflict.
  • CLI tests cover all flag mappings, selected-project fallback, ID/name/order resolution, ambiguous names, one-line JSON output, and non-zero failures without interactive prompts.
  • Manual acceptance: use Codex to create a phase and draft scenario, update the scenario, add and edit two checks, remove one check, rename and remove the phase, and confirm each result immediately in the existing web UI. Start a run, verify all eight operations fail with 409, finish it, and verify the same command succeeds.
  • Run pnpm lint, pnpm typecheck, pnpm test, pnpm build, and package the CLI to confirm the new commands appear in caracara --help.

Phase requirements

Agent use

No human data transfer

An interactive Codex session can complete all eight operations by invoking commands and reading their results. The user never copies scenario JSON, check IDs, or generated patches between tools.

Evaluation

A running evaluator cannot author

Once caracara run creates its running record, every phase or scenario write for that project fails server-side until finalization. The rule holds for CLI, web, and direct Convex mutation callers.

Data model

One live authored record

Inspecting the schema after implementation shows no scenario-version, proposal, activation, or undo storage. A successful change updates only the live phase or scenario data and its existing navigation metadata.
