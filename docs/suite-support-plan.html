Implementation plan

Suite support

Let a Caracara project define named suites that select any subset of its existing phases, then run only the selected phases without changing the phase model.

Complete Revision 3 One vertical implementation phase

Context

One project, several useful cuts

Caracara currently runs one scenario, one phase, a prefix of phases, or every phase. That works for a single linear evaluation, but it cannot name reusable non-contiguous selections such as phases 1, 2, and 4 for a landing-page evaluation or phases 2 and 3 for a demo evaluation.

A suite adds that selection without creating another execution hierarchy. Phases stay project-owned and globally ordered. A suite stores checkmarks against those phases. The same phase may appear in several suites. Each checkbox label shows both the phase number and its full name, such as Phase 2: Landing page. 

Public experience suite:
✓ Phase 1: Shared setup
✓ Phase 2: Landing page
  Phase 3: Main application
✓ Phase 4: Demo / trial

caracara run --suite public-experience
Runs phases 1, 2, and 4 in that order.

Suite authoring belongs only in the signed-in web app. The CLI may select and execute a suite, but it will not create, edit, or delete one.

Locked decisions

Global requirements

Data model

Suites select phases

A suite belongs to one project and has a name, stable project-unique slug, and a duplicate-free set of phase IDs. It does not own copies of phases, scenarios, dependencies, or checks.

Execution

Project phase order wins

Suite membership is unordered. Execution filters the existing phase plan by membership and keeps the project phase order. A suite containing phases 1, 2, and 4 skips phase 3 and executes 1, 2, then 4.

Access

Frontend-only authoring

Only authenticated frontend Convex mutations create, update, or delete suites. Do not add suite operations to the public v3 authoring route or the eight CLI authoring commands. Apply the existing project ownership checks and project-run authoring lock.

Compatibility

Existing run modes stay unchanged

A bare run still evaluates every runnable phase. Single-scenario, phase, and through-phase modes keep their current behavior. Suites are optional, so existing projects need no generated default suite or data migration.

Lifecycle

Changes do not rewrite history

Removing a phase removes its membership from every suite. Removing a suite does not touch phases or scenarios. Suite runs snapshot the selected suite name and slug, so later suite edits or deletion do not make old run records misleading.

Scope

Keep the first version narrow

Do not add nested suites, tags, suite-specific phase ordering, suite copies, suite-specific prompts, environment defaults, run-history filtering, or scenario-level suite membership. Use existing shadcn components and add no dependency.

Phase 01

Ship suite selection end to end

Add suite storage, the frontend editor, selective local execution, durable run metadata, and verification as one usable change.

Implement suites as a small project-owned record with embedded phase membership. The execution path reads that record and filters the phase plan already produced by Caracara. It does not create a second ordering algorithm.

  • Add a suites table with projectId, name, slug, phaseIds, and timestamps. Index it by project and by project plus slug.
  • Add signed-in Convex queries and mutations for the Suites workspace. Validate ownership, project-unique slugs, duplicate-free same-project phase IDs, and the existing authoring lock.
  • Extend the read-only execution API and CLI with caracara run --suite <slug>. Filter the existing execution plan and preserve project phase order.
  • Add run mode suite plus requested suite name and slug snapshots. Show the suite target in run details without adding a new history filter.
  • Update the product specs alongside the implementation so the many-to-many membership and frontend-only authoring boundary become source-of-truth decisions.

Phase requirements

Storage and contracts

Persist validated memberships

Add shared Suite schemas and types, Convex storage, conversion helpers, and ownership helpers. Permit an empty suite so phase deletion cannot violate storage invariants, but return a clear CLI error when a selected suite contains no runnable scenarios.

Navigation

Add the Suites route

Add /projects/[projectSlug]/suites, extend WorkspaceKind, add a Suites icon and label, and order the project dropdown exactly as Project, Suites, Phases, Scenarios, Runs. Refresh and browser history must preserve the route.

Frontend

Use one checkbox per phase

Follow the existing two-panel project workspace. List suites with their selected phase count on the left. On the right, edit name and slug, then show every phase in project order with a shadcn Checkbox labeled Phase N: <phase name>. Include create, Save, Revert, and confirmed delete actions plus empty, loading, validation, and locked states.

CLI execution

Select one suite by slug

Add --suite <slug> as an execution-only flag. Reject combinations with --scenario, --phase, or --through-phase. The authenticated execution endpoint resolves the suite inside the selected project and returns only member phases in global order. Missing, empty, or non-runnable suites fail before run creation with a specific message.

History and cleanup

Keep targets intelligible

Store the suite name and slug used by each suite run and show them in run details. Remove deleted phase IDs from suite memberships inside the phase-removal mutation. Include suites in project deletion. Deleting or renaming a suite must not alter prior run snapshots.

Verification

Prove both overlapping selections

Update the domain, storage, execution, API, authoring, frontend, navigation, and package specs. Add focused contract, Convex, execution-selection, CLI-option, cleanup, and component tests. Manually create suites for phases 1, 2, 4 and phases 2, 3, confirm overlap and persistence, run each suite, inspect run metadata, test phase deletion, and verify existing run modes. Finish with pnpm lint, pnpm typecheck, pnpm test, and pnpm build.
